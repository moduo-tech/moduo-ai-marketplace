# Moduo Astro project rules

Use this as a source for a short section in the target project's `AGENTS.md`. Merge it with existing project guidance; do not overwrite project instructions. If Claude Code uses a `CLAUDE.md`, import `AGENTS.md` with `@AGENTS.md` or merge the same section there.

- Inspect `package.json`, `astro.config.*`, Tailwind configuration, existing layouts and components before editing. Match the installed Astro and Tailwind versions, routing mode, package manager, and established design tokens.
- In an existing project, inspect and preserve its theme and visual language before laying out new UI. Reuse its typography, palette, spacing, radii, shadows, breakpoints, component patterns, and assets unless the user requests a redesign.
- Look for an available design in project references and connected design tools even if the user has not mentioned one. If a Penpot design exists, use the Penpot MCP to inspect its pages, components, styles, assets, and relevant measurements before implementing the UI. Derive or update the project theme from that design first, then build components and pages from the theme. Do not guess design values that can be read from Penpot.
- If no design exists, tell the user what visual conventions the project already has and ask whether to preserve or evolve them before laying out new UI. For a new project, ask for a palette, typography direction, visual references, and key component preferences. Establish the theme first, then develop the visual style with the user's answers; do not invent a complete aesthetic without consulting them.
- Define reusable design values through the installed Tailwind version's theme mechanism (`tailwind.config.*` or CSS `@theme`) and semantic tokens where appropriate. Use theme-backed utilities for colors, fonts, spacing, radii, shadows, and breakpoints wherever the theme can express them. Keep literal hex colors and arbitrary values in the theme definition, not repeated across templates, components, or stylesheets. Add a token when a repeated design value is missing; use a one-off value only when it is truly exceptional and explain why.
- Prefer semantic `.astro` components and static HTML. Add client-side JavaScript only for behavior that needs it; keep initialization correct across Astro client-side navigation when the project uses it.
- Name every variable and parameter for its purpose; never use single-letter names, including loop variables and test data.
- Add short, explicit comments that explain the responsibility of a module, component, or non-obvious block and the reason for decisions that are easy to misread. Keep comments accurate as code changes; avoid narrating every statement.
- In `.astro` markup, use HTML comments (`<!-- Start: ... -->` and `<!-- End: ... -->`) to delimit major visual sections or component groups. Name the section clearly so a developer or AI can scan the page structure. Avoid comments around individual trivial elements.
- Extract every meaningful visual section, repeated block, or independently understandable part of a page into a named component. Pages should read as a composition of small components instead of long HTML templates. Give each component one clear responsibility and keep its props explicit.
- Split code by responsibility into small, reusable modules. Put pure transformations and shared helpers in the project's `utils` convention, external API or CMS access in `services` or adapters, and domain logic in the project's existing `lib` or equivalent. Keep UI components free of unrelated fetching and transformations; avoid duplicated logic.
- Tailwind first when Tailwind is installed. Start with unprefixed mobile styles, then use the project's configured breakpoints. Use CSS only for behavior or styling that Tailwind utilities cannot express clearly; explain exceptions in the change summary.
- Do not write inline `<svg>` markup into HTML or `.astro` templates, including through icon components that emit inline SVG. Use an external SVG asset through `<img>` or another approved asset path. Give informative images meaningful `alt` text and decorative images an empty `alt`.
- Treat responsive quality as a behavior to verify: no horizontal overflow, clipped text, overlapping controls, inaccessible menus, or broken focus at target widths and around relevant breakpoints.
- When changing a localized route or shared component, check every configured locale, language metadata, locale links, and SEO metadata. Do not assume Spanish and English in other projects.
- Reuse the project's test and check commands. Add a focused test when behavior is changed, and run browser checks for visible layout or interaction changes. Report any check that could not run and why.
- Keep secrets out of code, fixtures, screenshots, and reports. Do not silently convert a failed CMS request into a successful empty state unless the project explicitly defines that behavior.

These are Moduo conventions. Existing code that predates them is review evidence, not an instruction to refactor unrelated files.
